# 完整复盘提交协议

本文件是默认完整复盘的强制门禁。先完成事实账本，再成稿；不能边提取边写最终答案。

## 状态门禁

完整复盘依次经过四个状态：

1. `DATA_READY`：数据完整度已按实际字段确认，状态冲突已处理
2. `LEDGER_COMPLETE`：固定事实模板全部填写，缺失数据逐项标记
3. `DRAFT_ALLOWED`：成稿前检查通过，才允许组织完整复盘正文
4. `REVIEW_COMPLETE`：成稿前条件仍成立，实际 Markdown 通过交付结构检查，并完成人工语义核验

不得跳级。没有达到 `DRAFT_ALLOWED` 时，禁止因为已经找到主要结论而提前成稿。

## 完成的定义

覆盖过某个英雄或事件不等于完成该栏目。每个必填字段必须满足以下任一条件：

- 已填入数据事实及其分析
- 明确标为“无法确认”，并说明缺少哪个字段或画面
- 明确标为“不适用”，并说明原因

空白、只写一句总评、只列KDA或只列技能次数，均计为未完成。

区分字段限制与栏目缺失：个别无法从数据得知的微观细节可以带具体原因标记，不要求伪造；若缺失证据使整个必需栏目无法形成结论，栏目应标为 `limited`，最终交付只能是部分复盘。不可把全部字段都填“无法确认”再宣称该栏目已完成。

## 固定事实模板

### 全局博弈思路，共1—3个

- 争夺的核心资源
- 一方的合理计划
- 另一方的合理反制
- 可观察信号
- 数据支持的实际选择；与推导计划分开
- 实际结果及后续地图影响
- 重打调整及其代价
- 反证与替代解释
- 基于当时可知信息的决策质量；与最终胜负分开
- 事实、模型判断和无法确认的边界

每个博弈必须能被后续关键团战验证或推翻。禁止把模型推导写成玩家真实意图；用户提出亲历信息后允许修正。

### 每一路

- 对位双方与理论任务
- 双方核心5、10分钟经济/补刀/反补/经验；15分钟作为对线后发育单列
- 两名辅助各自0分钟基线、6分钟累计、净新增伤害
- 双方二人组0—6分钟伤害与核心发育转化
- 0—10分钟击杀、死亡、补给压力、离线和可确认的支援
- 10—15分钟打野、游走、击杀、塔经济和补发育
- 第一座相关塔及地图后果
- 纯对线结论、对线后发育结论、该路结构性后果

### 每名核心，共六名

- 英雄、位置、理论职责
- 本局首要/次要胜利职责；是持续输出发动机、空间/前排、保护点、控制枢纽或目标转化点中的哪些
- 需要赋能的队友、必须限制的敌方英雄，以及履责成功的可观察信号
- 5/10/15/20/25/30分钟经济；比赛不足该时长时标不适用，超过30分钟则补关键后期节点
- 纯对线结果与对线后补发育
- 核心装备顺序、购买时间、使用次数、针对性与强势窗口
- 参战率、总输出、关键阶段输出、主要输出对象
- 关键技能/BKB如何创造或错过输出窗口
- 团队赋能：是否维持阵型、保护持续输出点、创造第二轮技能时间；不适用或数据不足时说明
- 所有关键死亡及其后果；买活、买活经济与买活战果
- 建筑伤害、Roshan/Aegis参与、团胜后的地图转化
- 职责完成度、最重要贡献、最大失误
- 与对方同位置的明确横向结论

六名核心可以共用一张曲线数据表，但每名核心必须另有独立分析段落。禁止用一张简表和一句总评代替六核审计。

### 每名辅助，共四名

- 对线压制与己方核心发育转化
- 视野、反眼、开雾与信息贡献
- 控制、救人、先反手和关键技能
- 关键死亡逐项判断其战术价值
- 装备与资源是否匹配职责
- 最终职责完成度

### 每件关键装备

关键装备的选择和事实纪律见 [equipment-review.md](equipment-review.md)。每件必须填写：

- 玩家、位置、物品和购买时间
- 组件流、拆分、重组或出售；无法确认时说明，不能把购买日志当成完整库存历史
- 当时战局、职责与获得的新能力或取舍
- 针对的敌方英雄、技能或装备；无法确认具体对象时说明
- 购买前最后一波相关战斗与购买后第一波相关战斗
- 整场使用次数与相关团战窗口内使用记录
- 对输出、控制、存活、击杀或撤退的实际影响
- 对队友生存、阵型、持续输出点和目标转化的影响
- 后续Roshan、Aegis、塔、高地、基地或无转化
- 装备窗口兑现、错过或无法确认
- 证据等级

每名玩家还必须有完整出装路线结论，包括最正确装备决策、最大装备问题和资源是否匹配职责。只列购买时间、最终六格或出装方向不算完成。

### 每名BKB持有者

- 购买时间
- 至少一个高价值窗口和一个低价值/未覆盖窗口；不存在时说明
- 战前是否已购买；是否送达或位于主背包无法确认时说明
- 团战窗口内使用记录
- BKB期间的伤害、击杀、技能与承伤
- BKB结束后的控制、输出和团战结果
- 是否维持前排位置、阻止敌方切入或让队友完成第二轮输出
- 证据等级

### 每代Aegis

- Roshan时间与击杀方
- 正常拾取或 `AEGIS_STOLEN`
- Aegis持有者与阵营
- 击杀方、持有方和最终受益方是否相同
- 持盾后的第一场关键战斗
- 第一条命的资源交换；是否能确认盾命而非实死
- 第二条命的输出、击杀、撤退或死亡
- 第一条命对团队空间和持续输出点的价值；低伤害不自动等于低价值
- 后续Roshan、塔、高地、基地或无转化
- 证据等级

### 每个关键技能

- 理论职责
- 整场总次数与已识别团战窗口次数
- 至少一个高价值实例和一个低价值/未覆盖实例；确实不存在时说明
- 与队友技能、BKB、Aegis和买活的联动
- 改变了谁的输出窗口
- 后续击杀、经济、Roshan、建筑或基地结果
- 事实、推断和无法确认的边界

只列技能次数不算完成关键技能矩阵。

### 每波决定性团战

- 时间与地点/目标
- 战前经济、经验、装备、BKB、买活、Aegis、兵线和建筑
- 本波核心博弈：只选一个最能解释结果的命题
- 双方在该命题下的合理思路与反制
- 开团方、第一目标、第一轮技能与承伤者
- 第一阶段：控制、爆发、BKB和最先失去战力的人
- 第二阶段：BKB结束后的输出窗口、核心接管或脱节
- 发动机—赋能者关系：谁需要连续输出，谁创造时间和生存条件，这组关系是否被打断
- 收尾：击杀、撤退、追击和存活
- 战后经济/经验变化及Roshan、塔、兵营、基地转化
- 最大贡献、最大失误、关键转折
- 结果验证：谁赢了本波核心博弈
- 重打一次只修改一个优先级的具体方案
- 博弈思路的事实、模型判断和未知边界
- 反证、替代解释及决策质量；胜利不能单独证明决策正确

阶段概述或一句“某方团灭”不算完成团战复盘。

### 用户每一次死亡

- 时间
- 死亡前任务与战场状态
- 直接原因
- 可见信号与当时选择
- 团队随后损失或收益
- 死亡前是否完成本局首要职责，是否让队友存活、输出或完成目标
- 分类：战术死亡、可接受死亡、明显失误或下限级失误
- 替代操作
- 证据等级

用户死亡必须逐次填写；死亡较多时可以用逐行表格，但不能合并成一句笼统结论。

## 内部覆盖表

进入成稿前必须得到以下结果：

- 比赛身份、补丁与数据完整度：`1/1`
- 全局博弈思路：`1—3/1—3`，均已写明计划、反制、结果与证据边界
- 三路：`3/3`
- 四名辅助0—6分钟压制：`4/4`
- 六核：`6/6`
- 四辅助全局职责：`4/4`
- 六核装备路线：`6/6`；四辅助功能装：`4/4`；用户出装路线：`1/1`
- BKB窗口：`实际持有者数/实际持有者数`；Aegis生命周期：`实际代数/实际代数`
- 关键技能：天辉`2—4/2—4`，夜魇`2—4/2—4`
- 决定性团战：通常3—5波，每波核心博弈`1/1`；数量例外有理由与全时间轴证据，窗口唯一且与全局博弈关联
- 用户死亡：`实际死亡数/实际死亡数`
- 输出对象、建筑、Roshan、买活：`4/4类已检查`；高风险装备与买活冲突：`已检查`
- 事实、推断、未知标签：`已完成`

必需栏目未完成时继续补充可获取的证据；确实无法完成则标为部分复盘，列出栏目及限制，不循环补写空话。正常不存在的内容可带证据标为不适用。

### 两阶段机器门禁

按 [ledger-schema.md](ledger-schema.md) 填写版本2账本。`analysis_coverage_template` 只保留兼容展示用途；修改其数量、required 或状态不能让验收通过。程序根据实际 `analysis` 记录、原始数据和装备审计计算覆盖。全局博弈和单波博弈必须有正文、具体来源引用及相互关联；数量不能替代内容。

成稿前运行：

`python scripts/extract_match_facts.py --check-ledger <事实账本.json> --stage draft`

只有 `passed=true`、`allowed_status=DRAFT_ALLOWED` 且原始证据已人工核对时，才组织完整复盘正文；无需提前把状态填写为已完成。

正文保存后运行：

`python scripts/extract_match_facts.py --check-ledger <事实账本.json> --stage final --review-markdown <复盘.md>`

最终检查重新核对源数据、实际分析记录、证据引用、比赛 ID 和15章正文。输出 `passed=false` 或非零退出码时，不得宣告完整复盘。无法运行脚本的环境执行相同人工覆盖检查，并写明“人工验收，未运行机器门禁”。

机器通过只证明结构和引用可解析，不证明文字中的因果关系成立。最后逐项核查：引用确实支持所述结论；博弈没有伪装玩家意图；每波只突出一个核心命题；正文与账本一致；中文命名正确；限制没有被藏在总结之外。

数量通常为3—5波，但若实际不足、零关键战斗或需要更多才能解释比赛，可在 `analysis.fight_selection` 填写 `reason`、`timeline_crosscheck` 和证据。只因 `teamfights` 条目少不足以申请例外，还必须检查击杀、曲线和目标；全局博弈仍须用实际事件检验。机器只核对例外材料齐全，合理性由语义核验负责。

## 数值结论标签

首次出现数值化结论时必须标明：

- `比赛统计`：JSON或可靠比赛数据直接给出的数值
- `模型判断`：根据本局证据给出的评分、责任比例或强弱比例
- `经验估计`：缺少足够统计样本的机制性估计

“对线六四开”“责任35%”“表现7.5分”等默认不是统计值。若没有可验证样本，必须紧邻标注为模型判断或经验估计。

## 固定交付结构

默认完整复盘必须严格使用以下顺序：

1. 比赛结论与用户概览
2. 数据完整度与限制
3. 阵容胜利条件
4. 全局博弈思路（1—3个）
5. 三路对线
6. 中期节奏与经济/经验拐点
7. 关键装备、BKB与强势窗口
8. 关键技能矩阵
9. 决定性团战（通常3—5波；每波一个核心博弈）
10. 六核独立审计与同位置比较
11. 四辅助职责
12. 用户每次死亡与个人改进
13. 责任排序或贡献排序
14. 最终结论
15. 完整性验收摘要

可以用表格承载重复数据，但不能合并或省略章节。

机器交付检查使用以上15个章节名称；主标题中的数量说明可放在括号内，章节按同一层级顺序排列。分篇交付时同时保存一份合并 Markdown，最终检查针对合并文件。检查章节不代表认可正文分析质量。

## 分段交付

若完整复盘过长，可以分为连续的上、中、下篇或编号章节：

- 每一部分开头标注范围，例如“复盘进行中：第1/3部分”
- 中间部分不得使用“完整复盘结束”“最终完成”等措辞
- 必须保存尚未完成的覆盖表并继续后续章节
- 最后一部分补齐全部章节后，才可标记 `REVIEW_COMPLETE`

## 最终验收摘要

完整复盘末尾用一行简短展示：

`验收：全局博弈1—3个已完成｜三路3/3｜辅助压制4/4｜六核6/6｜四辅助4/4｜装备六核6/6、辅助4/4、用户1/1｜BKB持有者N/N｜Aegis N/N｜关键技能双方已完成｜团战N/N且每波博弈1/1｜用户死亡N/N｜输出/建筑/Roshan/买活已检查`

若任何数字不足，必须写“部分复盘”并列出缺项，不能显示通过。

## 三条不可绕过的警告

1. 覆盖过某个英雄或事件，不等于完成该栏目；只有模板全部填写才算通过。
2. 禁止为了缩短篇幅，将六核审计、关键技能矩阵或决定性团战压缩成一句总评。
3. 数值化主观判断必须注明它是比赛统计、模型判断还是经验估计。
4. 出现装备名称或购买时间不等于完成装备审计；只有与能力、战斗、使用证据、结果和证据等级建立因果链才算完成。
5. 博弈思路是可讨论的模型判断，不是玩家意图事实；每波只能突出一个最能解释结果的核心博弈。
